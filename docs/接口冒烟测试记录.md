## 四、核心业务闭环（订房 → 入住 → 登记消费 → 退房 → 结算）

> 以下为同一次后端进程内按顺序执行的请求与真实返回，单号与金额可直接与数据库核对。
> 客人：张伟（guestId=1，GOLD 黄金会员，初始预存余额 120000 分 = 1200.00 元）。

### 1. 查客人（证件脱敏）与可分配房间

```
GET /api/front/guests?keyword=张伟                     （前台令牌）
→ code=200 records[0]: id=1 realName=张伟 memberLevel=GOLD
                        maskedIdCard=500102********0011  balanceCents=120000

GET /api/front/rooms/available?typeId=1&checkIn=<今日>&checkOut=<后天>
→ code=200 共 3 间：8801、8802、9806（均为 FREE 的标准大床房）
```

### 2. 房价试算（房价策略优先于会员折扣）

```
GET /api/public/quote?typeId=1&checkIn=2026-12-05&checkOut=2026-12-07&roomCount=1
→ code=200 { typeName=标准大床房, nights=2, roomCount=1,
             originUnitPriceCents=29800, unitPriceCents=32800, discountRate=100,
             priceSource="房价策略：周末价", totalCents=65600, depositCents=30000 }

GET /api/front/quote?typeId=1&checkIn=<今日>&checkOut=<后天>&guestId=1   （前台令牌）
→ code=200 priceSource="房价策略：周末价" unitPriceCents=32800 totalCents=65600
           depositCents=30000
```

说明：2026-12-05~12-07 落在 `rate_plan` 1 号策略（标准大床房「周末价」2026-10-01~12-31，
32800 分/晚）内，因此**按策略价执行且不再叠加会员折扣**（`discountRate=100`）；
无生效策略的日期才走"门市价 29800 分 / 会员价 26800 分 × 会员折扣"。

### 3. 创建预订

```
POST /api/front/reservations
{"guestId":1,"typeId":1,"roomId":1,"checkInDate":"<今日>","checkOutDate":"<后天>",
 "roomCount":1,"guestCount":1,"channel":"FRONT_DESK","specialRequest":"高楼层无烟房"}
→ code=200 单号=RS202610090002  总额=65600 分（656.00 元）  押金=30000 分（300.00 元）
           价格来源=房价策略：周末价  nights=2  roomNo=8801
           notice=预订保留至入住当日 18:00，超时未到店将自动释放房间

GET /api/room/1                                        （前台令牌）
→ code=200 status=BOOKED    ← 预订后房态由 FREE 转为 BOOKED

POST /api/front/reservations（同房同期重复下单）
→ code=400 房间 8801 在该日期区间已被预订，请选择其它房间或日期
```

### 4. 办理入住（分配房间 + 押金由预存余额抵扣）

```
POST /api/front/reservations/{resId}/checkin {"roomId":1,"idCard":"500102199005120011"}
→ code=200 roomNo=8801  depositCents=30000  paidByBalance=true
           guestBalanceAfter=90000   ← 客人预存余额 120000 → 90000 分
           checkOutDate=<后天>
           notice=退房时间为 <后天> 12:00 前，逾期将加收房费

GET /api/room/1
→ code=200 status=OCCUPIED   ← 入住后房态变为在住

POST /api/front/reservations/{resId}/checkin（再次办理）
→ code=400 当前预订单状态为 已入住，无法办理入住
```

数据库核对（`guest_transaction`）：

```sql
SELECT tx_no, tx_type, amount_cents, balance_after, biz_type, remark
FROM guest_transaction WHERE biz_id = <resId> ORDER BY id;
-- TX<日期>xxxx  CONSUME  -30000  90000  RESERVATION  办理入住收取押金 300.00 元
```

### 5. 入住自动生成账单

```
GET /api/front/bills/by-reservation/{resId}            （前台令牌）
→ code=200 billNo=BL202610090001  status=UNSETTLED
           roomChargeCents=65600（房费 656.00 元）
           depositCents=30000（押金抵扣 300.00 元）
           totalCents=35600（应收 356.00 元）
```

### 6. 登记客房消费（两个入口）

```
GET /api/bill/consume-items?category=餐饮&status=ON_SALE   （前台令牌）
→ code=200 餐饮类共 3 项，示例：中式早餐 / 3800 分

POST /api/front/bills/{billId}/consume {"consumeItemId":1,"quantity":2,"remark":"上门送餐"}
→ code=200 itemName=中式早餐  quantity=2  amountCents=7600
           consumeChargeCents=7600  payableCents=43200

POST /api/bill/by-reservation/{resId}/consume {"consumeItemId":1,"quantity":1,"remark":"按预订ID登记"}
→ code=200 amountCents=3800  payableCents=47000
```

说明：账单相关操作统一以**账单 ID** 为路径参数；为兼容按预订 ID 调用的写法，
额外提供 `/api/bill/by-reservation/{reservationId}/consume` 兼容入口，内部先解析出账单 ID
（该兼容入口源于缺陷 D-02，见第七节）。

### 7. 账单优惠（需填原因）

```
POST /api/front/bills/{billId}/discount {"amountCents":2000,"reason":"会员生日优惠"}
→ code=200 discountCents=2000  payableCents=45000

POST /api/front/bills/{billId}/discount {"amountCents":1000}      （缺 reason）
→ code=400 必须填写优惠原因，便于审计追溯
```

### 8. 办理退房（按实际晚数重算房费）

```
POST /api/front/reservations/{resId}/checkout
→ code=200 stayNights=1  roomChargeCents=42800（含延迟退房费）
           consumeChargeCents=11400  discountCents=2000  depositCents=30000
           payableCents=22200  billNo=BL202610090001
           notice=房间已置为待打扫，请到账单页完成结算

GET /api/room/1
→ code=200 status=CLEANING  cleanStatus=DIRTY
```

金额校验：房费 42800 + 消费 11400 − 优惠 2000 − 押金抵扣 30000 = **22200 分（222.00 元）**，
与 `payableCents` 完全一致。退房时按"实际住宿晚数 × 成交单价 × 房间数"重算房费，
若当前时点超过 14:00 再加延迟退房费。本次闭环在 18:00 之后执行，命中"18:00 后加收全天"分支，
因此房费明细为 `房费（实际 1 晚 × 1 间 + 延迟退房费）32800 × 1 = 42800`（32800 + 10000 延迟退房费）。

**账单金额的完整演变（可与 `bill` / `bill_item` 逐条核对）**：

| 阶段 | 触发动作 | 房费 | 消费 | 优惠 | 押金抵扣 | 应收 `total_cents` |
| --- | --- | --- | --- | --- | --- | --- |
| 预订 | `POST /front/reservations` | 65600 | 0 | 0 | 0 | 65600（此时尚未登记押金） |
| 入住 | `POST .../checkin` | 65600 | 0 | 0 | 30000 | 35600 |
| 登记消费 | `POST .../consume` × 2 | 65600 | 11400 | 0 | 30000 | 47000 |
| 优惠 | `POST .../discount` | 65600 | 11400 | 2000 | 30000 | 45000 |
| 退房 | `POST .../checkout` | **42800**（按实际晚数重算 + 延迟退房费） | 11400 | 2000 | 30000 | **22200** |
| 结算 | `POST .../settle` | 42800 | 11400 | 2000 | 30000 | 实收 22200 |

### 9. 客房服务反馈打扫完成

```
POST /api/room/clean/1                                 （客房服务令牌）
→ code=200 已反馈打扫完成，房间转为空闲
GET /api/room/1
→ code=200 status=FREE  cleanStatus=CLEAN
```

房态闭环：FREE → BOOKED → OCCUPIED → CLEANING/DIRTY → FREE。

### 10. 账单结算（押金抵扣与退还）

```
POST /api/front/bills/{billId}/settle {"payType":"CARD","refundToBalance":true}
→ code=200 roomChargeCents=42800  consumeChargeCents=11400  discountCents=2000
           depositCents=30000  paidCents=22200（应收 222.00 元）
           refundCents=0  payType=CARD  guestBalanceAfter=90000
           status=SETTLED

POST /api/front/bills/{billId}/settle                  （重复结算）
→ code=400 账单已结算，无需重复操作
```

说明：本次结算应收 22200 分，低于入住时已抵扣的押金 30000 分，但按 `settle` 的实现
"应收 = max(0, 房费 + 消费 − 优惠 − 押金抵扣)"，`net = +22200` 为正，因此
`refundCents=0`、`paidCents=22200`，客人预存余额保持 90000 分不变（押金已整额抵扣、无剩余可退）；
若 `net` 为负（押金有剩余）则差额退还客人并写 `guest_transaction` 的 `REFUND` 流水。

数据库核对：

```sql
SELECT id, bill_no, room_charge_cents, consume_charge_cents, discount_cents,
       deposit_cents, total_cents, paid_cents, refund_cents, pay_type, status
FROM bill WHERE id = 14;
-- 14  BL202610090001  42800  11400  2000  30000  22200  22200  0  CARD  SETTLED

SELECT item_type, item_name, unit_price_cents, quantity, amount_cents
FROM bill_item WHERE bill_id = 14 ORDER BY id;
-- ROOM     房费（实际 1 晚 × 1 间 + 延迟退房费）  32800   1    42800
-- CONSUME  中式早餐                              3800   2     7600
-- CONSUME  中式早餐                              3800   1     3800
-- OTHER    优惠减免                             -2000   1    -2000

SELECT tx_no, tx_type, amount_cents, balance_after, biz_type, biz_id, remark
FROM guest_transaction WHERE guest_id = 1 ORDER BY id;
-- TX202610090001  CONSUME   -30000  90000  RESERVATION  19  办理入住收取押金 300.00 元
-- TX202610090002  CONSUME   -22200  90000  SETTLE       14  账单 BL202610090001 结算补收 222.0 元（刷卡）
-- TX202610090003  DEPOSIT    10000  100000 DEPOSIT      NULL 客人自助预存
-- （第 4、5 条为验收脚本第二次运行产生的重复演练流水）
```

## 六、AI 能力接口

### 1. 知识库问答（RAG，带引用来源）

```
POST /api/ai/ask?scene=QA {"question":"入住和退房时间分别是几点？押金怎么收？"}   （前台令牌）
→ code=200 degraded=false model=deepseek-chat promptVersion=v1.0 latency≈1500ms
   citations: 2 条，首条《退房与账单结算规则》(0.137)
   answer: 入住时间为当日 14:00 之后，离店时间为次日 12:00 之前……
           押金标准：标准房与高级房 300 元，家庭房 500 元，套房 1000 元……
```

检索链路：文档入库 → 按 220 字符切分（重叠 40 字符）→ 本地 TF-IDF 向量化 →
余弦相似度排序取 Top-4 → 低于阈值 0.08 视为无答案 → 命中片段与来源一起写入提示词，
答案下方展示引用来源供人工核验。

### 2. 无答案处理

```
POST /api/ai/ask?scene=QA {"question":"帮我写一段爬取酒店点评的 Python 代码"}   （前台令牌）
→ code=200 citations=0
   answer（开头）：知识库中没有找到相关依据。……
                   （引导联系前台 分机 0 或值班经理，未编造房价与政策）
```

### 3. 提示词注入拦截

## 七、降级路径验证

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| 未配置密钥 | 不设置 `HOTEL_AI_API_KEY` 启动后提问 | 返回「【AI 服务未启用】当前未配置模型密钥，无法生成智能回答。你可以：① 联系前台或值班教练获取准确信息；② 在系统设置中由管理员配置模型密钥后重试。」（**注**：该文案中的"值班教练"是沿用另一课程项目的措辞，酒店场景应为"值班经理"，见遗留问题 I-05），其它功能正常，模型标记为 `local-fallback` |
| 上游异常 / 断网 | 断开外网后提问 | 按 `ai.max-retries=2`、`ai.retry-backoff-ms=800` 自动重试后返回「【模型服务暂时不可用】已自动重试仍未成功，本次未使用模型输出，避免返回不准确内容……」，`ai_call_log` 记录 `success=0` / `degraded=1` 与错误原因 |
| 触发限流 | 一分钟内连续提问超过 `ai.rate-limit-per-minute=20` 次 | 返回「【触发调用频率限制】短时间内提问过于频繁，已被系统限流以控制调用成本。请稍等 1 分钟后重试，或直接查看下方知识库检索结果」 |
| 关闭 AI 总开关 | `HOTEL_AI_ENABLED=false` 启动 | `GET /api/ai/status` 返回 `enabled=false`，调用走降级文案，评测接口仍可离线运行 |
| 模型输出不合法 JSON | 报价单生成时模型首次输出不合格 | 自动追加修复提示词重试一次；仍不通过则返回 200 但 `valid=false` 并说明未写入数据库，**不产生脏数据** |
| 知识库检索不可用 | 删除全部知识库文档后提问 | `hitCount=0`，走无答案提示词，明确告知无依据并引导人工，不编造 |

耗时、重试次数、是否降级与错误信息，管理端「数据概览」与「AI 评测」页面可查看场景分布与成本估算

## 九、遗留问题

| 编号 | 现象 | 影响 | 处理计划 |
| --- | --- | --- | --- |
| I-01 | 登录令牌存于服务端内存（`TokenStore`），后端重启后全部登录态失效 | 单机部署影响可接受；联调或截屏期间如重启了后端，页面会收到一次 401 提示 | 属预期行为，不是接口缺陷。生产可改为 Redis 或 JWT（令牌读写已封装在 `TokenStore`）；使用中若重启后端，重新登录即可 |
| I-02 | 知识库向量为本地 TF-IDF 稀疏向量 | 同义改写的问题召回率偏低（相似度多在 0.10~0.28 区间） | 后续接入 embedding 接口，只需替换 `TextVectorizer.vectorize` 与 `fromJson` |
| I-03 | 客人预存为模拟入账，未接真实支付网关 | 无法真实收款，只能演示业务流程 | 可接微信支付 Native 扫码；`guest_transaction` 已预留 `tx_type`、`biz_type`、`biz_id` 字段用于对账 |
| I-04 | `sql/hotel_system.sql` 的口令字段为 `__INIT__` 占位符 | 直接导入后不能立即登录，必须先启动一次后端生成散列 | 已在演示脚本与测试报告中明确该步骤；这是为"仓库中不出现可反推口令内容"而做的主动取舍 |
| I-05 | ~~AI 降级文案与注入拒绝话术沿用另一课程项目措辞~~ **已修复** | 原提示为"值班教练""健身相关问题"，`needHumanConfirm` 保留 `WRITE_TRAIN_PLAN`/`DELETE_MEMBER` 等健身语义行动名 | 已改为"联系前台（分机 0）或值班经理"、"咨询酒店业务相关问题"，风险行动名改为 `DEDUCT_DEPOSIT`/`WRITE_QUOTE`/`REFUND`/`BLACKLIST_GUEST`；修改后重新编译并复测 54 项断言全部通过 |
| I-06 | 退房延迟退房费按当前钟点简化取值（`hour >= 14` 收 5000 分、`hour >= 18` 收 10000 分） | 与知识库"12:00~14:00 加收半天房费、14:00 后加收全天房费"的表述只是量级近似，不是按成交单价的精确比例 | 本次闭环在 18:00 后执行，实测房费 42800 = 32800（1 晚）+ 10000（延迟退房费），该分支工作正常；建议改为按成交单价的 50%/100% 计算并补充单元测试 |

| I-08 | ~~结算"补收差额"写入 `guest_transaction` 时 `amount_cents = -paid`，但 `balance_after` 未发生变化~~ **已修复** | 原实测 `TX202610090002 CONSUME -22200 90000`，前后余额都是 90000 分，对账时易被误读为"扣款未生效" | 已改为 `tx_type=ADJUST`、`amount_cents=0`、`balance_after` 保持实际余额，备注注明"（刷卡，未动用预存余额）"；修复后实测流水为 `CONSUME -30000 → 90000`（入住收押金）与 `ADJUST 0 → 90000`（结算补收 222 元走刷卡），语义清晰 |
